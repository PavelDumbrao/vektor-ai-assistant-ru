# Общий runtime «Вектора» на одном VPS

## Цель и границы

Программы и одинаковые библиотеки хранятся один раз; личные данные, ключи,
память, плагины и процессы остаются отдельными для каждого Linux-пользователя.
Этот модуль переносит существующие private-runtime, не меняя их модели,
Telegram-права или содержание переписки. Это не контейнерная изоляция:
администратор сервера и инфраструктура по-прежнему общие.

## Устройство

```text
/opt/vektor/                         root:root, пользователям только чтение/запуск
  python/                           один управляемый Python нужной версии
  cache/uv/                         закрытый кэш администратора
  releases/hermes-<code>-<deps>/
    hermes-agent/                   сохранённая версия кода
    venv/                           окружение с абсолютными путями этой версии
    runtime.json                    отметка готовности
  tools/                            закреплённые версии общих CLI
  profiles/<owner>.json              регистрация owner → release, без секретов
  backups/                          закрытые резервные копии переноса

/home/<owner>/.hermes/
  hermes-agent -> /opt/vektor/releases/.../hermes-agent
  config.yaml, .env, SOUL.md         личные, не переносятся в общий каталог
  plugins/, memories/, state.db     личные
```

Одинаковые файлы разных code releases используют hardlink. Исходные файлы из
домашних каталогов сначала копируются: общий файл никогда не является ссылкой
на изменяемый файл клиента. Различающиеся файлы сохраняются отдельно.
Одинаковые пакеты venv также физически общие через `uv --link-mode hardlink`.
Это не объединяет Python-процессы или их память.

Venv создаются заново в окончательных путях, а не переносятся: Python использует
абсолютные пути в launcher/shebang. Версии всех установленных distributions
должны совпасть с исходными. Локальный Hermes не собирается и не выполняется от
root: привязка кода оформляется обычным `.pth` и metadata; smoke выполняется от
целевого Linux-пользователя с временным `HERMES_HOME`.

## Порядок переноса

Работает администратор VPS, не агент клиента. Сначала прочитайте планы и
проверьте версии, состояние служб и свободное место. Никаких реальных ключей
в команды не подставляется.

1. Разместите `prepare_runtime.py`, `switch_profile.py` и
   `../passive-secretary/shared_runtime_layout.py` рядом в закрытом root-owned
   служебном каталоге. Обновите три административных скрипта секретаря вместе
   с `shared_runtime_layout.py`; остальные файлы его bundle сохраняйте.
2. Выполните read-only план:
   `python3 prepare_runtime.py --owners client1 client2`.
3. Подготовьте новый общий каталог:
   `python3 prepare_runtime.py --owners client1 client2 --apply`.
   Работающие профили этот шаг не переключает. Продолжение прерванной
   подготовки разрешено только с `--resume` и теми же проверенными входами.
4. Проверьте импорты, точные версии, hardlink/inode и отсутствие права записи
   у обоих пользователей в общий код. Контроль исходного кода должен пройти.
5. По одному профилю: `python3 switch_profile.py --owner client1`, затем
   `python3 switch_profile.py --owner client1 --apply`.
6. Дождитесь `state=active`, нового PID и `Telegram=connected`. Только после
   проверки первого профиля переключайте второй.

`switch_profile.py` требует idle-состояние, сохраняет старый runtime и unit,
оставляет прежний путь `ExecStart`, задаёт `UMask=0077` и личный короткий
`TMPDIR=/tmp/vkr/<uid>`. Каталоги восстанавливаются при загрузке через отдельную
tmpfiles-конфигурацию; это не общий каталог сессий браузера.
При ошибке готовности скрипт возвращает старый unit, runtime и ссылки CLI.
Если он обнаружил независимое изменение unit/ссылки, он останавливается для
ручной проверки, а не затирает работу другого оператора.

## Общий браузер

`install_agent_browser.py` устанавливает закреплённый `agent-browser` из npm
registry с обязательной проверкой SHA-512 integrity. Lifecycle scripts npm не
выполняются; чужие платформенные бинарники не распаковываются; лицензия
сохраняется. Существующий системный Chrome используется повторно.

Пример вызова: `python3 install_agent_browser.py --version 0.26.0
--expected-integrity <проверенный-SRI-из-registry>`.

Общими являются CLI и Chrome, но не daemon, browser profile, cookies, storage
или сокеты. Проверка: запустить два браузера от разных Linux-пользователей с
одинаковым именем сессии и разными приватными socket/profile директориями;
ввести разные тестовые значения и убедиться, что они не смешиваются. После
проверки закрыть только созданные тестовые сессии.

Electron, наборы иконок, web/TUI devDependencies и остальные frontend-пакеты не
нужны для базового Telegram gateway и в server runtime не устанавливаются.
GUI при необходимости готовится администратором отдельным комплектом.

## Приёмка и освобождение места

- Оба gateway запущены от своих пользователей; `HERMES_HOME` и рабочие каталоги
  остались личными; токены и конфигурации не изменены.
- Проверены Telegram identity, импорты документов, private plugins, layout
  retention и отсутствие новых ошибок загрузки.
- Другой пользователь не читает личную `.env`/БД/каталоги и не меняет общий код.
- Одинаковые зависимости — один inode, а не просто одинаковые версии в копиях.
- Перед удалением старых **программных** деревьев создайте сжатые архивы,
  проверьте tar/контрольные суммы и порядок восстановления. Данные профилей не
  архивируются этим переносом и не удаляются.
- Старый Python нельзя удалять, пока его использует другой процесс, например
  отдельный onboarding-сервер. Такой экземпляр остаётся до отдельного переноса.
- Старый `uv` cache удаляется только как восстановимый кэш программ, после
  проверки отсутствия зависимых симлинков и готовности runtime backups.
- Диск измеряется с учётом hardlink: один общий `du` по нужным каталогам либо
  подсчёт уникальных `(device, inode)`. Сумма независимых `du` завышает объём.

## Откат после успешной миграции

Используйте закрытый backup конкретного owner и его `migration.json`.
Остановите только его gateway; убедитесь, что текущая ссылка указывает на
зарегистрированную версию. Верните старое программное дерево на исходный путь,
восстановите unit и прежние CLI, удалите только созданную для этого переноса
регистрацию и tmpfiles-конфигурацию, затем выполните daemon-reload/start.
Если backup сжат, сначала восстановите его в закрытый служебный каталог,
сверив checksum. Старый venv должен вернуться на исходный абсолютный путь.
Ключи, настройки и переписку при откате не восстанавливайте поверх новых данных.

## Обновления

Профиль не обновляет общий runtime на месте и не запускает в нём `pip install`
или `hermes update`. Администратор готовит новую отдельную версию и проверяет её
до переключения. Не снимайте root ownership ради удобства обновления: один
клиент не должен менять программу, которую запускают остальные.

Проверенный upgrade уже зарегистрированных профилей на Hermes **0.21.0**:
[инструкция и patch-series](releases/v0.21.0/README.md). Начальный учебный
снапшот в корневом `hermes-agent/` остаётся отдельной сборкой 0.20.0; не
подменяйте им более новый managed runtime и не запускайте старый core installer.
